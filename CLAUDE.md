# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ESOS WebUI — a Nuxt 4 (Vue 3, SSR) web console for administering [ESOS](https://github.com/esos-project/esos) SAN storage nodes. The server drives one or more ESOS nodes **over SSH** (running shell commands and parsing their text output) and stores its own state (users, SAN credentials, alert thresholds, metrics) in a local **SQLite** database via Drizzle ORM. There is no ESOS API — everything is `ssh → run command → parse stdout`.

UI text defaults to **French** (`fr`), with English as secondary. Many code comments, error messages, and identifiers are in French — this is expected, match it.

## Commands

```bash
npm run dev            # dev server, hot reload, http://localhost:3000 (SQLite + migrations auto-created)
npm run build          # production build → .output/
npm run start          # run production build
npm run test           # full Vitest suite (vitest run)
npm run test:watch     # Vitest watch mode
npm run test:rbac      # single file: tests/api-rbac.test.ts
npx vitest run tests/<name>.test.ts   # run any single test file
npx vitest run -t "<name>"            # run tests matching a name
npx drizzle-kit generate              # generate a migration after editing server/db/schema.ts
npm run audit:theme    # scripts/audit-theme.mjs — flags hardcoded theme classes
```

There is **no lint script and no standalone typecheck script**. Types come from Nuxt (`tsconfig.json` extends `.nuxt/tsconfig.json`, generated by `nuxt prepare` / `postinstall`). Native deps (`better-sqlite3`, `argon2`, `ssh2`) require a build toolchain and are kept **external** from the Nitro bundle (see `nuxt.config.ts`) — don't try to bundle them.

Requires **Node ≥ 22**. `NUXT_ENCRYPTION_KEY` and `NUXT_JWT_SECRET` must be set (see `.env.example`); the first is AES-256 for encrypting stored SAN SSH credentials, the second signs session JWTs.

## Architecture

### SSH is the data plane
All SAN data is obtained by running commands over SSH and parsing stdout — there is no ESOS REST API.

- `server/utils/ssh-session-manager.ts` — one persistent SSH connection per node, multiplexed into up to 10 exec channels, with keepalive + auto-reconnect.
- `server/utils/ssh-pool.ts` — `SSHPool`, one `SSHSessionManager` per active `sanId` (multi-SAN / "v2").
- `server/utils/ssh-runtime.ts` — the routing layer. `withSanContext(sanId, fn)` binds a SAN to the async context (`AsyncLocalStorage`); downstream `getActiveSSHManager()` calls then resolve to that SAN's manager. Falls back to a legacy single-node singleton ("v1") when no SAN rows exist. **When adding an API route that touches a SAN, run the work inside the SAN scope, don't call `getActiveSSHManager()` bare.**
- `server/utils/parsers/*` — pure text→structured parsers (mdstat, lvm-json, corosync, dmidecode, smart, drbd, …). Each has a matching `tests/*.parser.test.ts`. Keep parsers pure and unit-tested; this is where most correctness bugs live.
- `server/utils/*.service.ts` (e.g. `raid-overview.service.ts`, `lvm-overview.service.ts`) — orchestrate `ssh exec → parser → DTO` for a feature area.

### Request scoping (multi-SAN)
Read routes use `resolveScopedSanIdForRead` / `runReadWithSanScope` (`server/utils/san-request-context.ts`): explicit `?sanId=` wins; exactly one active SAN is implicit; **more than one active SAN with no `?sanId=` is a 400**. Mutations require `?sanId=` (`requireSanIdQuery` in `san-query.ts`) and go through `assertSanWritableFromEvent`, which 403s if the SAN row is marked read-only.

### Auth & RBAC
- `server/middleware/auth.ts` runs on every `/api/*` request (except the `PUBLIC_API_PREFIXES` allowlist): validates the session JWT cookie, checks `sessionVersion` against the DB (so disabling a user / password change revokes live sessions), then calls `enforceApiRbac`.
- `server/utils/api-rbac.ts` is the **single source of truth for route permissions**, kept import-light so it's testable without Nitro. Three roles: `admin` > `operator` > `viewer`. **Mutations are deny-by-default** — a `POST/PUT/PATCH/DELETE` with no matching rule is 403. Rules are ordered specific→general and the first match wins, so ordering matters. Edit permissions here, and keep `tests/api-rbac.test.ts` in sync.
- Auth providers: local (argon2), OIDC (`openid-client`), and LDAP/AD (`ldapjs`) — see the `auth-providers-*` and `ldap-*`, `oidc-*` utils.

### Persistence
- `server/db/index.ts` — `getDB()` opens SQLite (WAL, FK on) and **applies Drizzle migrations on startup**. Migrations are not a manual step at runtime; only regenerate them (`drizzle-kit generate`) after schema changes.
- Schema in `server/db/schema.ts`; access goes through `server/db/repositories/*.repository.ts` (don't scatter raw queries).

### Startup order
`server/plugins/` are numbered and run in order: `0.database` → `1.app-version` → `2.binaries-storage`, then `collector` (metrics collection) and `ssh`. `server/utils/admin-seed.ts` creates a default `admin` account on first boot and prints the generated password to logs **once**.

### Frontend
Nuxt pages in `pages/*`, auto-imported components in `components/*` (no path prefix), Pinia stores in `stores/*`, composables in `composables/*`. `utils/*` (repo root, distinct from `server/utils/*`) holds **client-side** pure helpers, each with a matching test. The header SAN selector drives `useSelectedSan` / `useNavigationContext`, which supply the `?sanId=` that scopes API calls. Theming is class-based (`@nuxt/ui` + Tailwind, cookie-stored color mode) — use theme tokens, not hardcoded colors (`npm run audit:theme` enforces this; see `docs/theming.md`).

## Conventions

- Adding a SAN-scoped read endpoint: wrap the handler body in `runReadWithSanScope(event, ...)`. Adding a mutation: call `assertSanWritableFromEvent(event)` and add an explicit rule in `api-rbac.ts`.
- New parser → new pure function in `server/utils/parsers/` + a `tests/*.parser.test.ts`. Feed it into a `*.service.ts`, not directly into a route.
- Design docs live in `docs/` (`SDD-*`, `deploy-*`, `theming.md`, `i18n.md`); code comments reference "SDD vX.Y" sections. Check `docs/` before large feature changes.

## Fork notes (not upstream)

- **Build heap lives in `.npmrc`, not the Dockerfile.** `.npmrc` sets `node-options=--max-old-space-size=4096`; npm passes it as `NODE_OPTIONS` to the scripts it runs, so `npm run build` in the Docker builder stage gets a 4 GB heap. On hosts with ≤ 16 GB RAM Node caps the heap at ~2 GB and `nuxt build` runs out of memory ("JavaScript heap out of memory"); above 16 GB Node already defaults to 4 GB, which is why upstream never hits it. Upstream's Dockerfile has no heap setting. Keep the fix in `.npmrc` so upstream Dockerfile changes merge without conflicts; when merging upstream, check that `.npmrc` still exists and that upstream hasn't added its own `.npmrc` or a `.dockerignore` entry excluding it. Check it's active with `npm config get node-options`. A runtime env var (compose `.env`, Helm `extraEnv`) does NOT help: the OOM happens during `docker build`.
